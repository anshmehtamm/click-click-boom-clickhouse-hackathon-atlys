Base-context consistency investigation

Conclusion: the base context is not wholly reliable as a current database description. It is accurate for the original core funnel subset, but it is stale after the addition of lifecycle and feature-event tables. It also contains a material contradiction in the stated data grain.

Confirmed and supported statements

  • Core row counts match the documented values: destination_card_clicked 1,000,000; application_started 154,413; document_uploaded 20,446; pay_now_clicked 14,739; purchase_completed 7,054.
  • The core funnel tables are currently one row per user and one row per application in the checked stages. For example, purchase_completed has 7,054 rows, 7,054 users, and 7,054 applications.
  • Duplicate and backfill rates are close to the stated envelope: duplicate_id is approximately 3% and is_back_filled approximately 2% in the checked core tables.
  • OS-null behavior is supported: in destination_card_clicked, all 59,485 NULL OS rows are Android rows, with no NULL OS rows outside Android.
  • The funnel convention is appropriate. Because timestamps become unreliable after document_uploaded, application_id matching with distinct counts is safer than windowFunnel or sequenceMatch for later stages. The documented 47.9% pay-to-purchase rate is consistent with the stored context and current row counts: 7,054 / 14,739 = 47.9%.

Material contradiction

The dataquality envelope says that every table is one-to-one between user_id and row. That is false for the expanded database:

This is expected for event-history tables, but the context should scope the one-row-per-user statement to the synthetic core funnel tables rather than calling it consistent across all tables. Visa sharing is also clearly multi-event per share: 6,503 rows correspond to 1,600 shares.

Stale or incomplete scope statements

  • The database currently contains 15 substantive tables plus materialized views and inner tables, not just the “current 8 tables” referenced by the envelope and several issue notes.
  • Several core tables described as Jan–Jun 2026 contain boundary records on July 1: document_uploaded, pay_now_clicked, application_started, and purchase_completed all have July 1 maxima. Visa-sharing events also include eight link_opened events on July 1. destination_card_clicked itself ends on June 30.
  • The envelope says its properties are consistent across all 8 tables, but the newer event tables use different timestamp types, identifiers, grains, and ingestion conventions. The statement is therefore stale even where the original eight-table observations remain valid.
  • The group_application_events context calls the current table’s existence “not independently verified,” while the database inventory confirms that group_application_events exists with 5,453 rows. That wording should be updated.

Known-issue correlation

  • K1: contradicted. The stored finding remains consistent: Gulf iOS pay-to-purchase conversion is higher, not lower, than non-Gulf iOS across versions.
  • K2: partially supported. The Android threshold-crossing rate is directionally higher than iOS, but the April timing claim has not been tested.
  • K6: contradicted on timing. SUMMER20 redemptions are approximately flat by month rather than showing a Q2 spike.
  • K7: contradicted. Monthly version shares remain approximately flat across 7.42.0–7.46.0, with no visible staged rollout.
  • K3–K5: remain untested because the required citizenship/retry, Schengen-destination, or channel/nudge analyses are not established by the current evidence.

Recommended context corrections

  1. Replace “every table is 1:1 user_id:row” with “the original core funnel tables exhibit a synthetic one-row-per-user pattern; lifecycle event tables are multi-row per user.”
  2. Replace “all 8 tables” with an explicit table-family scope and document the newer event tables separately.
  3. Change the Jan–Jun window to “primarily Jan–Jun, with July 1 boundary records in several tables,” or enforce a formal analysis date filter.
  4. Mark group_application_events as present and populated, while retaining its event-level grain and deduplication caveats.
